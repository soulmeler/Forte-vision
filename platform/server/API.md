# Vision Forte: сервер, API и подключение модели

Сервис реализован на Node.js ≥ 22.13, Express 5 и встроенном `node:sqlite`. Модель запускается на отдельном компьютере или GPU-сервере Forte; платформа подключается к нему по адресу API и ключу. Загрузка, сохранение, предпросмотр, проверка SHA-256 и жизненный цикл задач работают без модели. При отсутствии готовой модели анализ возвращает **503 `MODEL_NOT_READY`**, без фиктивных событий, уверенности или вердиктов.

## Запуск и хранение

Основной запуск описан в корневом README. Низкоуровневая точка входа: `node server/index.js`. Она читает `.env` через dotenv. `startServer(overrides)` экспортируется для встроенного запуска и тестов; возвращает `{ app, config, store, model, server, close, stop }`. `stop()` закрывает HTTP, потоки, workers и SQLite. `createApp(overrides)` создаёт приложение без прослушивания порта.

Постоянные данные:

- `DATA_DIR/vision-forte.sqlite`: метаданные видео, оригинальные имена, SHA-256, задачи, результаты и ошибки.
- `DATA_DIR/videos/<uuid>.video`: исходные файлы. Клиентские имена никогда не используются как путь.
- `DATA_DIR/tmp/<uuid>.upload`: временные загрузки. Прерывание удаляет недокачанный файл. При следующем старте удаляются оставшиеся служебные временные файлы и файлы без записи в SQLite.

Сервис рассчитан на **один процесс приложения на один DATA_DIR**. SQLite использует WAL и foreign keys; очередь выполнения хранится в памяти, метаданные задач — в SQLite. При перезапуске незавершённые задачи становятся `failed` / `SERVER_RESTARTED`. Автоматического повторного запуска нет. Уже готовые задачи и видео сохраняются. Не запускайте несколько копий приложения против одного хранилища: очистка служебных файлов и очередь не распределённые.

По умолчанию видео и связанные с ним задачи удаляются через 7 суток после загрузки. Очистка работает при старте и раз в час; активные задачи пропускаются. DELETE удаляет видео и все его задачи; при активном анализе возвращает 409. Журналирование исходных видео, кадров, API-ключей и описаний сцен отсутствует. Резервную копию базы/видео делайте при остановленном сервисе либо штатным SQLite backup с согласованным снимком каталога. Не копируйте только `.sqlite`, игнорируя WAL, у работающего сервиса.

## Конфигурация

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `FORTE_API_KEY` | обязательна | Ключ API самой платформы, не ключ сервера модели; минимум 24 символа, не размещать во frontend, git или URL |
| `HOST` | `127.0.0.1` | Адрес прослушивания |
| `PORT` | `3000` | HTTP порт |
| `LOCAL_AUTO_SESSION` | `false` | Только при явном `true`: выдавать браузерную сессию без ввода ключа на loopback |
| `PUBLIC_ORIGIN` | пусто | Обязательный точный HTTPS origin для публичного HOST, например `https://vision.example.org`; без завершающего `/` |
| `DATA_DIR` | `./data` | Каталог постоянных данных |
| `MAX_UPLOAD_MB` | `300` | Максимальный размер одного файла, десятичные MB; граница включительно |
| `MAX_STORAGE_MB` | `4096` | Сумма сохранённых видео и активных загрузок, десятичные MB |
| `RETENTION_DAYS` | `7` | Время хранения от даты загрузки |
| `JOB_TIMEOUT_MS` | `300000` | Дедлайн задачи, включая ожидание очереди; максимум 1260000 (21 минута) |
| `MAX_CONCURRENT_JOBS` | `1` | Число одновременно выполняемых задач, 1–4 |
| `MAX_PENDING_JOBS` | `10` | Максимум одновременно принятых задач, включая выполняющиеся |
| `MODEL_LOAD_TIMEOUT_MS` | `60000` | Лимит инициализации каждого worker |
| `MODEL_ADAPTER_MODULE` | пусто | Служебный путь к локальному ESM адаптеру; не нужен для подключения сервера модели через интерфейс |
| `MODEL_DIR` | `./models` | Только для служебных локальных адаптеров; веса отдельного сервера модели сюда не копируются |
| `FORTE_FFPROBE_PATH` / `FFPROBE_PATH` | `ffprobe-static` | Необязательный путь к ffprobe; FORTE-вариант имеет приоритет |
| `PYTHON_BIN` | `python3` | Только для готового Python-адаптера: путь к Python из нужного venv |

HTTP загрузка ограничена 180 секундами. Анализ имеет отдельный настраиваемый лимит после принятия задачи, включая очередь; по умолчанию пять минут. Недостающие/неподдерживаемые параметры среды не должны подменяться клиентскими значениями. При публичном развёртывании используйте TLS reverse proxy, сохраняющий исходный Host, с соответствующим лимитом тела/времени, и `LOCAL_AUTO_SESSION=false`. CORS не включён. Публичный HOST без HTTPS `PUBLIC_ORIGIN` запрещён. Ответ платформы `status: "ok"` не означает готовность сервера модели: проверяйте отдельно `model.ready`.

## Аутентификация и браузерная сессия

`GET /api/v1/health`, `/capabilities`, `/session` и `/regulatory-sources` доступны без ключа и не раскрывают данные видео. Для остальных данных нужен заголовок `X-API-Key: <key>` либо сессионная cookie.

`POST /api/v1/session`, `Content-Type: application/json`, тело `{ "api_key": "..." }` создаёт cookie `forte_session`: HttpOnly, SameSite=Strict, срок 8 часов; Secure при HTTPS. Тело ответа: `{ "authenticated": true, "expires_at": "ISO timestamp", "local_auto_session": false }`. Ключ не возвращается и не должен храниться в localStorage. Сессии находятся в памяти и прекращают действие при перезапуске.

При явно разрешённом локальном режиме POST с `{}` выдаёт сессию только при loopback HOST и loopback соединении. Это удобство личного запуска: локальные процессы устройства разделяют доступ. Для общих устройств отключите его. GET `/session` возвращает `{ authenticated, local_auto_session }`. DELETE `/session` удаляет текущую cookie и сессию, ответ 204.

API проверяет Host, Origin и `Sec-Fetch-Site`; запрос с другого сайта отклоняется даже при переданном ключе. Клиенты cURL без Origin поддерживаются. После десяти неверных ключей с одного адреса вход блокируется на 15 минут. Лимит загрузок — 60 запросов в час на адрес соединения. Это один служебный ключ и один набор данных, а не система пользовательских ролей или многопользовательская изоляция.

## Подключение отдельного сервера модели

Откройте в интерфейсе «Сервер модели» и задайте базовый адрес, например `http://192.168.1.10:8000/api/v1`, и API-ключ этого сервера, затем нажмите «Проверить и подключить». Сетевые запросы выполняет серверная часть платформы; браузер не обращается напрямую к серверу модели. Веса и GPU остаются на компьютере команды или сервере Forte.

Настройки подключения общие для текущего процесса платформы и хранятся только в памяти. После перезапуска их нужно задать заново. Ключ не возвращается клиенту и не записывается в localStorage или журнал. `FORTE_API_KEY` и cookie защищают API платформы; отдельный ключ сервера модели используется в исходящем заголовке `X-API-Key`. Эти ключи не взаимозаменяемы.

Маршруты требуют авторизованной сессии платформы либо её `X-API-Key`:

| Метод и URL | Назначение |
|---|---|
| GET `/api/v1/model/connection` | Состояние подключения и настроенный адрес без секретного ключа |
| PUT `/api/v1/model/connection` | JSON `{ "base_url": "http://192.168.1.10:8000/api/v1", "api_key": "SERVER_MODEL_KEY" }`: задать подключение и проверить готовность |
| POST `/api/v1/model/connection/check` | Повторно проверить связь и готовность настроенного сервера |
| DELETE `/api/v1/model/connection` | Удалить из памяти адрес и ключ, отключить анализ |

Все успешные ответы этих маршрутов имеют форму:

```json
{
  "connection": {
    "configured": true,
    "base_url": "http://192.168.1.10:8000/api/v1",
    "key_present": true,
    "authentication": "api_key",
    "persistence": "memory",
    "checked_at": "ISO timestamp",
    "error": null
  },
  "model": {
    "status": "ready",
    "ready": true,
    "name": "forte-vision",
    "version": "v1",
    "supported_categories": [],
    "transport": "remote_api"
  }
}
```

Без настройки `configured` и `key_present` равны `false`, адрес, аутентификация и дата проверки — `null`, модель имеет `status: "not_configured"`. Сам ключ никогда не включается в DTO. `DELETE` возвращает `200` с этим отключённым состоянием.

`PUT` требует оба поля и активирует настройку только после корректного ответа health с логическим `model.ready` (или `ready` для API команды). При `ready: false` доступный сервер сохраняется, но анализ не разрешается. Ошибка связи, ключа или формата health не заменяет прежнее подключение и возвращается как `{ "error": { "code", "message" } }`. `POST .../check` обновляет состояние: при неудаче возвращает DTO с `connection.error` и `model.ready: false`; без настройки — `409`.

Если `/health` на сервере модели общедоступен, успешная проверка подтверждает связь и заявленную готовность, но не валидность ключа. Авторизация окончательно проверяется запросом к защищённому маршруту анализа. `key_present` означает наличие введённого ключа, не успешный вход.

Ошибки подключения: `INVALID_MODEL_URL`, `INVALID_MODEL_API_KEY`, `REMOTE_AUTH_FAILED`, `REMOTE_UNAVAILABLE`, `REMOTE_TIMEOUT`, `REMOTE_REDIRECT_REJECTED`, `INVALID_REMOTE_RESPONSE`, `REMOTE_JOB_FAILED`. Сообщения очищены от исходных ошибок удалённого сервера. `PUT` и `DELETE` во время задач возвращают `409 MODEL_BUSY`, параллельное изменение подключения — `409 CONNECTION_BUSY`. Ключ должен содержать 1–4096 ASCII-символов без пробельных символов.

Изменение или отключение подключения при активных задачах запрещено. Допустимы HTTP(S)-адреса без встроенных credentials, query и fragment. Используйте адрес из сети, доступной серверной части платформы; для передачи через недоверенную сеть — HTTPS. Редиректы не используются, чтобы не передать ключ другому адресу.

### API команды: синхронный анализ видео

В `base_url` передаётся полный адрес `https://your-server.example/v1/analyze-video`. Окончание пути выбирает протокол `raw_video`; DTO сообщает `authentication: "bearer"`. Ключ передаётся как `Authorization: Bearer …`, без сохранения на диск. Запросы содержат `ngrok-skip-browser-warning: 1`, редиректы запрещены.

- `GET /health` относительно origin: `{ "ready": true, "base_model": "…/Qwen3-VL-4B-Instruct", "adapter": "checkpoint-96" }`.
- `POST /v1/analyze-video`: исходные байты загруженного видео, `Content-Type: video/mp4` или `video/quicktime`; без multipart, Excel и имени исходного файла.
- Синхронный ответ: `{ "result": { "status": "ok", "prediction": { "violation": false, "event_type": "none", "events": [], "insufficient_data": false }, "window_status_counts": { "ok": 1, "invalid": 0, "error": 0 }, "windows": [{ "status": "ok", "start_seconds": 0, "end_seconds": 2 }], "duration_seconds": 2 } }`.

У событий читаются `start_seconds`, `end_seconds`, `evidence`, `reason` и `event_type` (либо общий `prediction.event_type`). Таймкоды относятся к исходному видео. Кадр извлекается платформой в середине интервала через FFmpeg (`FORTE_FFMPEG_PATH` или команда `ffmpeg`). Ссылки на нормы не выдумываются. Сырые промпты, пути сервера и служебные трассы в результат платформы не сохраняются.

`violation: null`, `insufficient_data: true`, неполное покрытие или частично неудачные окна дают `review_required`. Отсутствующие таймкоды не заменяются нулём. Полная ошибка или некорректный ответ дают ошибку задачи. Время ожидания ограничено `JOB_TIMEOUT_MS`; остановка ожидания не отменяет вычисление на удалённом сервере.

### Альтернативный контракт асинхронных задач

Для базового адреса без окончания `/v1/analyze-video` сохраняется протокол `async_jobs`:

Платформа добавляет к `base_url` следующие пути и отправляет `X-API-Key` во всех этих запросах:

1. `GET /health` возвращает JSON `{ "model": { "ready": true, "name": "forte-vision", "version": "v1", "supported_categories": [] } }`. Готовность означает готовый инференс, не только запущенный HTTP-сервер.
2. `POST /analyze` принимает один файл в multipart-поле `file`, создаёт задачу и возвращает `202` с `{ "job_id": "id" }`.
3. `GET /jobs/:id` возвращает `status: "processing"`, пока идёт анализ, затем `status: "done"` с полями результата ниже либо `status: "failed"` с ошибкой. Обновление статуса не должно выдавать ошибку за пустой список нарушений.

Видео сначала сохраняется на платформе и передаётся серверу модели только по явному запуску анализа. Результат проверяется платформой по схеме, включая JPEG-кадры и границы времени, затем сохраняется с задачей.

Обычный OpenAI-совместимый `/chat/completions` не является этим контрактом. Если модель работает через такой runtime, HTTP-обработчик на сервере должен принять видео, подготовить кадры, вызвать модель и вернуть задачу и структурированный результат. Настройка адреса и ключа сама по себе не обучает модель и не подтверждает её качество.

Прекращение ожидания в интерфейсе не отменяет серверную задачу. При тайм-ауте или выключении платформы прекращается ожидание её ответа; отдельный сервер модели может продолжать вычисления, поскольку контракт не содержит отмены задачи. Срок хранения копий на сервере модели задаётся отдельно от хранения платформы.

## Ответы и ошибки

### Архивы видеозаписей и отчёты

Все маршруты архивов требуют сессию платформы или её `X-API-Key`. Ключ сервера модели используется только серверной частью при анализе.

| Маршрут | Назначение |
|---|---|
| `POST /api/v1/batches` | Один ZIP в multipart-поле `file`; `201 {batch}`. Только импорт, без запуска модели. |
| `GET /api/v1/batches` | `{batches}` — сохранённые архивы и счётчики статусов. |
| `GET /api/v1/batches/:id` | `{batch}` — записи, их статусы и компактные результаты без JPEG. |
| `POST /api/v1/batches/:id/analyze` | `202 {batch}` — запустить/продолжить очередь. JSON `{retry_failed:true}` также повторяет ошибки анализа для сохранённых видео. |
| `GET /api/v1/batches/:id/report.xlsx` | Excel: записи, ответы и комментарии модели, ошибки, события и таймкоды. Незавершённый отчёт явно помечен. |

`batch` содержит `id`, `original_name`, `created_at`, `status` (`ready`, `processing`, `paused`, `done`), `counts` (`total`, `queued`, `processing`, `done`, `failed`) и в подробном ответе `items`. Элемент списка содержит `id`, `original_name`, `video_id`, `status`, `job`, `error`. Компактный `job` сохраняет вердикт, необязательный `summary`, описания, таймкоды, ограничения и сведения о модели; кадры получают по обычному `/videos/:id` или `/jobs/:id`.

Импорт проверяет ZIP до извлечения, использует собственные UUID для файлов, проверяет CRC, размер после распаковки и квоту хранилища. Папки поддерживаются, служебные файлы macOS пропускаются. Ошибки обычных неподдерживаемых файлов видны в списке; опасный или повреждённый ZIP отклоняется целиком. Байты ZIP не сохраняются после импорта. Сам архив не отправляется модели: сервер получает отдельные видео по очереди.

Очередь архива хранится отдельно от короткой очереди инференса. После перезапуска платформы незавершённая задача фиксируется как ошибка, оставшаяся очередь приостанавливается и требует явного продолжения. Ошибка, ожидание или отсутствие результата никогда не экспортируются как «нарушений нет».

Время — ISO 8601 UTC, таймкоды — дробные секунды. Общая ошибка:

```json
{ "error": { "code": "MODEL_NOT_READY", "message": "Обученная модель пока не подключена или не готова." } }
```

В редком случае потери готовности после успешной multipart-загрузки `/analyze` ошибка также содержит `error.details.video_id`: видео сохранено и может быть повторно отправлено в анализ. HTTP 400 — неверный запрос, 401 — ключ/сессия, 403 — Origin/Host, 404 — неизвестная запись, 409 — видео ещё анализируется, 413 — превышен размер, 415 — формат/контейнер, 416 — Range, 422 — нечитаемое видео, 429 — очередь или частота, 503 — модель не готова, 507 — хранилище заполнено. Внутренние пути, stack traces и сообщения модели клиенту не передаются.

Модельное состояние:

```json
{ "status": "not_configured", "ready": false, "name": null, "version": null, "supported_categories": [] }
```

Возможные `status`: `not_configured`, `loading`, `ready`, `error`. Отдельного фиктивного процента прогресса нет.

| Метод и URL | Ответ/поведение |
|---|---|
| GET `/api/v1/health` | `{status:"ok",service:"vision-forte",model,timestamp}` |
| GET `/api/v1/capabilities` | `{formats:[".mov",".mp4"],max_upload_bytes,job_timeout_ms,model,authentication:{local_auto_session},features:{upload:true,preview:true,analysis},retention_days}` |
| GET `/api/v1/regulatory-sources` | Публичный справочник `{available,checkedAt,sources,...}` из `data/regulatory-sources.json`; проверка нормативного текста отдельно от результата модели |
| POST `/api/v1/videos` | Multipart, ровно одно поле `file`. 201 `{video}` |
| GET `/api/v1/videos?limit=20` | `{videos:[video],total}`; limit 1–100, новые первыми |
| GET `/api/v1/videos/:id` | `{video,latest_job}`; latest_job — последняя задача именно этого видео, либо null |
| GET/HEAD `/api/v1/videos/:id/content` | Исходное видео, авторизация cookie/ключ, Accept-Ranges, корректные 206/416; одиночные byte ranges |
| DELETE `/api/v1/videos/:id` | 204; во время задачи 409 `VIDEO_BUSY` |
| POST `/api/v1/videos/:id/analyze` | 202 `job`; повтор во время выполнения возвращает ту же задачу |
| POST `/api/v1/analyze` | Требуемый кейсом endpoint: multipart `file`, ключ `X-API-Key`; 202 `job` с обязательным `job_id` |
| GET `/api/v1/jobs/:id` | `job` с `processing`, `done` или `failed` |

`video`:

```json
{
  "id": "uuid", "original_name": "sample.mov", "size_bytes": 5253179,
  "mime_type": "video/quicktime", "sha256": "hex digest", "created_at": "ISO timestamp",
  "duration_sec": 25.934, "width": 464, "height": 848, "codec": "h264",
  "has_audio": false, "metadata_source": "ffprobe",
  "preview_url": "/api/v1/videos/uuid/content"
}
```

Метаданные могут быть `null`, если ffprobe недоступен. Наличие аудиодорожки — метаданные; звук не анализируется. Приём MOV/MP4 не гарантирует поддержку видеокодека браузером: ошибки воспроизведения отображает UI. Автоматического транскодирования нет. Проверяются расширение, поддерживаемая сигнатура ISO BMFF/QuickTime `ftyp`, размер, а при доступном ffprobe — читаемость и наличие видеодорожки. MIME от клиента не является доказательством формата.

GET `/regulatory-sources` возвращает каталог с `sources` (акты) и вложенными `provisions` (пункты). `checkedAt` — дата независимой проверки, `available:true` — каталог прочитан. При отсутствии файла возвращается `{available:false,checkedAt:null,sources:[]}`; некорректный файл даёт 503 `REGULATORY_CATALOG_UNAVAILABLE`. Каталог нормативов перечитывается при запросе и может обновляться отдельно; рекомендуется атомарная замена JSON. Проверка текста источника не подтверждает нарушение в видео.

`job` при выполнении:

```json
{ "job_id": "uuid", "video_id": "uuid", "status": "processing", "stage": "queued",
  "source": "server", "created_at": "ISO timestamp", "updated_at": "ISO timestamp", "model": {"transport":"remote_api"} }
```

`source` равен `server` для отдельного сервера модели и `local` для служебного локального адаптера. `stage`: `queued`, `analyzing`, `done`, `failed`. `done` добавляет `verdict`, `violations`, `warnings`; в режиме действий — также `review_required: true`, `observed_events` и `analysis.coverage`; `failed` добавляет `error:{code,message}` без вердикта. Ошибки модели: `MODEL_ERROR`, `INVALID_MODEL_RESULT`, `MODEL_NOT_READY`, `MODEL_WORKER_ERROR`, `MODEL_WORKER_EXITED`, `JOB_TIMEOUT`, `SERVER_RESTARTED`, `SERVER_SHUTDOWN`. В браузере опрашивайте задачу каждые 1–2 секунды, останавливайтесь на done/failed, отличайте сетевую ошибку от завершения модели.

При повторном открытии записи или перезагрузке страницы используйте `latest_job` из GET `/videos/:id`. Это та же схема `job`, выбранная по `created_at DESC, rowid DESC`, с привязкой к точному ID видео. `done` восстанавливает результат и кадры, `failed` — сообщение ошибки, `processing` — опрос `/jobs/:job_id`. Отсчёт времени возобновляется от серверного `created_at`, а не начинается заново. При `null` видео ещё не анализировалось. Загрузка нового видео по-прежнему возвращает только `{video}`.

## Служебный интерфейс локального адаптера (не сценарий подключения сервера)

Этот интерфейс оставлен для разработчиков существующих локальных адаптеров. Для отдельного сервера используйте подключение по API выше; установка весов в платформу не требуется.

1. Положите веса, tokenizer/конфигурацию и необходимые локальные зависимости в выбранный каталог. Проверка не должна скачивать веса или обращаться к внешнему AI API. Только визуальный анализ, без идентификации лиц и использования звука.
2. Создайте ESM файл адаптера, экспортирующий `async createAdapter({ modelDir })`. Функция возвращает объект ниже. Это контракт, **не пример работающей модели**:

```js
export async function createAdapter({ modelDir }) {
  let model;
  return {
    metadata: { name: "ваша модель", version: "ваша версия", supported_categories: [] },
    async load() {
      // Загрузить обученные веса из modelDir и выполнить локальную самопроверку.
      // Присвоить model; выбросить исключение при ошибке.
    },
    isReady() { return Boolean(model); },
    async predict({ videoPath, video, signal }) {
      // Декодировать только видео; video содержит id/duration_sec/width/height/codec/mime_type.
      // Вернуть результат схемы ниже. Слушать signal.abort для остановки своей работы.
      // Не возвращать демонстрационный ответ вместо анализа записи.
      throw new Error("Подключите реальный inference вашей модели");
    }
  };
}
```

3. Укажите `MODEL_ADAPTER_MODULE=./models/adapter.mjs`, `MODEL_DIR=./models/forte`, перезапустите сервер. `/health.model.ready` становится true только после успешных `load()` и `isReady() === true`. Ошибка инициализации оставляет интерфейс и загрузку доступными, но блокирует анализ.
4. Каждый worker загружает собственную копию модели; увеличивайте MAX_CONCURRENT_JOBS только при достаточной памяти. Весь inference выполняется в отдельном worker thread. По дедлайну он получает abort и прекращается; зависший worker заменяется. Фабрика дополнительно получает `signal` и `registerProcess(pid)`, `load({signal})` получает сигнал остановки инициализации. Если адаптер создаёт внешние процессы, запускайте их как отдельную группу (`detached:true` на Unix), немедленно вызывайте `const release = registerProcess(child.pid)`, а при завершении процесса — `release()`. Родительский сервер уничтожает зарегистрированные группы при shutdown, дедлайне, ошибке инициализации и падении worker. Также слушайте abort и реализуйте необязательный `close()` для собственных ресурсов. Прекращение Node worker само по себе не убивает незарегистрированные процессы. При явном `isReady() === false` во время задачи slot становится недоступным; исправьте модель и перезапустите сервис.

## Схема результата модели

Готовый ответ сервера модели (`status: "done"`) содержит следующие поля. Локальный адаптер, если он используется отдельно, возвращает ту же структуру без `status`:

```json
{
  "verdict": "violation",
  "violations": [{
    "type": "имя категории",
    "timecode_sec": 22.4,
    "description": "Наблюдаемое действие и причина необходимости проверки человеком.",
    "evidence_frames": [{ "timestamp_sec": 22.4, "image_base64": "чистый base64 JPEG, без data: префикса" }],
    "rule_refs": [{ "title": "Название документа", "section": null, "url": "https://example.org/source", "verified": false }]
  }],
  "warnings": []
}
```

`review_required` требует `review_required: true`, пустой `violations`, список `observed_events` (может быть пуст) и `analysis.coverage`. Для каждого действия передаются `task`, `type`, `start_sec`, `end_sec`, `timecode_sec`, `description` и 1–3 JPEG. Окна имеют приблизительные границы; `coverage.complete` означает только завершение запланированных окон. `no_violation` требует пустой `violations`, `violation` — непустой. Максимум 20 нарушений или 100 наблюдаемых действий, от 1 до 3 JPEG на событие, до 1 MiB на кадр и до 8 MiB JSON результата. Сервер проверяет base64, маркеры/структуру JPEG, размеры до 8192 px, конечные неотрицательные таймкоды и попадание в длительность при известной длительности. Это структурная проверка, не независимая оценка достоверности или полный декодер изображения. Описание до 4000 символов; нормативные ссылки только HTTP(S), до 5 на событие. Не выдумывайте нормативные основания: пустой `rule_refs` разрешён и отображается как отсутствие источника. Соответствие нормативной части кейса команда проверяет отдельно. `warnings` описывают ограничения охвата. Если сервер выполняет только распознавание действий, используйте `review_required`, даже если наблюдаемых действий нет; не выдавайте это за проверку отсутствия нарушений. Неизвестные поля, в том числе фиктивный confidence, не передаются клиенту.

**Происхождение `rule_refs[].verified`.** Это входное заявление адаптера: валидатор возвращает `true` только при буквальном `ref.verified === true`, иначе `false`. Валидатор проверяет структуру ссылки и HTTP(S) URL, не открывает источник и не сверяет его с `data/regulatory-sources.json`. Поэтому клиент отображает «Адаптер отметил источник как проверенный» и пояснение «Проверка источника не подтверждает правовую оценку события».

Контракт `rule_refs` остаётся `{title,section,url,verified}`. Для подключения модели фиксируйте в `title` точный ID/номер акта, в `url` официальный источник, в `section` пункт/подпункт, ID положения каталога при наличии и применённую редакцию с датой её действия. Записи о проверке и версии нормативов храните в локальном реестре адаптера; дополнительные JSON-поля сейчас отбрасываются. Не путайте дату посещения/проверки с датой действия редакции. При неизвестной дате события, редакции или применимости используйте `verified:false` и `warnings`. Даже проверенный текст нормы не доказывает юридическую квалификацию наблюдаемого события.

## Служебный мост к Python (не используется при подключении сервера по API)

В `server/adapters/python-local.mjs` реализован реальный запуск локального Python. Он **не содержит модели**. Укажите:

```dotenv
MODEL_ADAPTER_MODULE=./server/adapters/python-local.mjs
MODEL_DIR=./models/forte
PYTHON_BIN=/absolute/path/to/venv/bin/python
```

Создайте `MODEL_DIR/inference.py` с двумя режимами CLI:

```text
python inference.py --health --model-dir DIR
  stdout: {"ready":true,"name":"model-name","version":"v1","supported_categories":[]}

python inference.py --predict /absolute/video.path --model-dir DIR --metadata-json '{...}' --visual-only
  stdout: один JSON объект результата по схеме выше
```

`--health` обязан проверить наличие/совместимость весов и готовность реального inference, не всегда возвращать true. У health лимит 15 секунд. Диагностику выводите в stderr, результат — единственным JSON в stdout. Возвращайте ненулевой код при ошибке. Мост не использует shell, ограничивает stdout, прекращает процесс и его группу при отмене на Unix и ничего не отправляет в сеть. На Windows остановка группы дочерних процессов требует реализации в вашем адаптере.

Каждая проверка запускает новый Python-процесс: загрузка весов входит в бюджет задачи. Для тяжёлой модели используйте собственный адаптер с постоянным локальным процессом/runtime и корректной отменой. Базовый Python-мост удобен для интеграции готового inference CLI; производительность и качество конкретной модели должны быть измерены после подключения.

## Проверка

`npm test` выполняет интеграционные Node-тесты с временными SQLite/каталогами и отдельными портами: auth/origin/session, загрузка и её границы/прерывание/заполнение диска, MOV/MP4 заголовок, сохранение после перезапуска, Range/HEAD, удаление, очередь, дедлайн и замена worker, ошибки/готовность, строгая схема кадров и ссылок.

`tests/server/fixtures/test-adapter.mjs` — исключительно синтетический тестовый fixture. Не указывайте его как MODEL_ADAPTER_MODULE при демонстрации или развёртывании и не представляйте его ответы как вывод обученной модели. Тестовые кадры не взяты из банковских видео.

Перед приёмкой сервера модели: прогнать отложенную выборку без пересечения одинаковых SHA, проверить оба вердикта и несколько событий, вручную сопоставить кадры/таймкоды/основания, измерить полный ответ в пределах пяти минут. Успех API-тестов не доказывает качество модели. Перед публичным использованием отдельно настроить TLS, ограничение доступа, дисковый объём, резервирование и эксплуатационное наблюдение; загрузки предназначены для доверенного дататона/локального контура, не анонимного публичного файлообменника.

### Решение сотрудника

`PUT /api/v1/videos/:id/review` (с авторизацией) принимает
`{"decision":"safe","job_id":"UUID завершённой проверки"}`.
Допустимые решения: `violation`, `safe`, `model_error`.
Результат должен принадлежать этому видео, иметь статус `done` и вердикт
`violation` или `review_required`. Активная обработка возвращает 409.
Ответ: `{video: ...}`, где `video.review` содержит `decision`, `job_id`,
`reviewed_at` (UTC), либо `null`, если решение не принято.
Поле доступно также в списке видео и элементах архива. Повторный PUT заменяет
решение. Ответ модели не меняется. При повторном анализе старое решение остаётся
связано с прежним `job_id`; интерфейс не показывает его как решение нового результата.
Решение, дата и ID результата включаются в Excel в отдельные колонки.
